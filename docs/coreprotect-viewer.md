# Панель CoreProtect · FLEXITY

Панель подготовлена локально. По умолчанию выключена. Рабочий Minecraft, CoreProtect, платёжный сервис, firewall, DNS и reverse proxy при разработке не изменялись.

## Совместимость и источник данных

Read-only проверка установленного JAR: **CoreProtect 24.1**, константа **API_VERSION = 12**. В конфигурации: `use-mysql: true`, `api-enabled: true`, MariaDB на localhost, база `coreprotect`, префикс `co_`. Пароль основного CoreProtect в панель не переносится.

Официальный [контракт v12](https://docs.coreprotect.net/api/version/v12/) и исходники [тега v24.1](https://github.com/PlayPro/CoreProtect/tree/v24.1) сверены с сигнатурами установленного JAR. `LookupOptions` ограничивает user/time/location/radius/offset/count, но не задаёт конец периода, material/exclude/action/text. Типизированный поиск блоков требует конкретный Bukkit Block; legacy partial lookup исключает action > 3 и не даёт query timeout. Поэтому выбран **отдельный read-only MariaDB адаптер**, а не чтение всех записей с фильтрацией в памяти или блокировка Folia-потока. SQLite в этом релизе не поддерживается.

Адаптер привязан к проверенной схеме 24.1. При другой версии/API панель не запускается. Доступность категорий определяется по реально доступным таблицам/полям; отсутствие таблицы скрывает категорию. Наличие таблицы не гарантирует, что логирование категории было включено в момент события. Старые/удалённые записи панель восстановить не может.

## Доступ и безопасность

Кнопка `🔎 CoreProtect` находится в функциях администратора, экране суперадминистратора и Root. Её видят только пользователи с внутренней ролью Admin/SuperAdmin/Root **и** текущим Telegram-статусом `administrator`/`creator` в `coreprotectWeb.accessChatId`. Для нескольких имеющихся chatId выбран отдельный явный источник ACL, без hardcode. Используется общий `TelegramApi.chatAdministrator`, которым пользуется `/offtop`.

Сервер проверяет raw `Telegram.WebApp.initData` по [официальному HMAC-SHA256 алгоритму Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), принимает auth_date не старше 5 минут (допуск будущего времени 30 секунд), проверяет ID только после подписи. Новая сессия всегда повторно проверяет Telegram; текущая — каждые 30 секунд при обращении. Открытая панель также перепроверяет доступ каждые 35 секунд. Внутренняя роль проверяется каждый раз; ошибки Telegram закрывают доступ.

Сессия — случайный 256-битный токен, серверное состояние живёт 10 минут. В браузере токен находится только в памяти JavaScript, без localStorage/cookies/URL. Он передаётся заголовком Authorization по HTTPS. GET `/api/session` принимает initData **в заголовке**, не в query string; `/api/capabilities`, `/api/materials` и `/api/lookup` требуют Bearer session. Персональные результаты не доступны по обычной ссылке. Нет сторонних CDN; единственный внешний скрипт — официальный Telegram WebApp SDK. CSP, frame-ancestors для Telegram Web, nosniff, no-store, no-referrer; wildcard CORS отсутствует.

Нельзя включать access log заголовков Authorization, query string с текстовым фильтром или тел запросов/ответов в reverse proxy. CSP запрещает inline-script; полученные строки выводятся через textContent. Audit переиспользует `TelegramModeration.audit`: TG ID, открытие/тип поиска, target, период, мир/координаты/радиус/страница. Текст чата, команд, auth/session, результаты и пароли туда не попадают.

## Что можно искать

- По текущему нику, UUID и прежнему нику через `username_log`. Неоднозначный ник требует UUID.
- По координатам: куб XYZ с ограниченным радиусом; радиус 0 означает один точный блок, включая Y. Для двойного сундука каждая половина имеет отдельные координаты.
- Блоки: сломал/поставил/взаимодействовал; убийства сущностей; контейнеры: добавил/забрал; операции предметов и инвентаря; входы/выходы; чат, команды, таблички.
- Появление сущностей не заявляется: в установленном API 12 нет соответствующего контракта. BLOB metadata/NBT не десериализуются и не отдаются браузеру.
- «Операции инвентаря» — тот же набор источников, что в InventoryAPI v12: установка блоков, контейнерные операции и item-транзакции, с нормализацией направления. Это журнал операций, **не снимок содержимого инвентаря**. Общая timeline не дублирует их отдельной копией.
- Периоды 30 минут/2/12/24 часа/7/30 дней и свой диапазон в пределах maxDays. Мир, категория/действие, include/exclude материалов (до 8), координаты/радиус; starts/contains для чата/команд/табличек. Материалы нормализуются через Bukkit Material; SQL параметры связаны PreparedStatement. Проценты и подчёркивания текстового поиска считаются буквальными символами.
- Результаты: новые сначала, обычно 50, максимум 100 на странице. Карточка события показывает время, игрока/UUID, действие, материал/количество, координаты, rollback-флаг и текст, если он есть. Переходы: игрок → его события, контейнер → точная история, координаты → события рядом. Координаты копируются.

После достижения maxOffset нужно сузить период. Общий точный COUNT всех строк не запускается. Страницы фиксируют верхнюю границу времени, но база остаётся живой: при позднем поступлении старых событий или внешнем purge состав страниц может измениться. Пустой результат не доказывает отсутствие событий в прошлом.

### Галочки фильтров и копирование команды

Галочки отдельно включают игрока, мир, координаты, категорию/действие, include/exclude материалов и текст. Выключенные поля не проверяются формой и не отправляются backend, даже если в них остались старые значения. Период всегда ограничен. Для контейнеров можно указать только ник и период; координаты включаются отдельно, а переход «История этого контейнера» включает точный блок автоматически. Поиск без игрока и координат по-прежнему запрещён.

В обоих фильтрах материалов есть «Выбрать из списка»: поиск по русскому названию или английскому ID, несколько выбранных позиций и повторное нажатие для удаления. Короткие порции списка догружаются кнопкой «Показать ещё» только в DOM, без HTTP/SQL. Вписывать названия через запятую также можно: например, `алмаз, Алмазная руда, minecraft:emerald_ore`; регистр, лишние пробелы и е/ё не мешают. `materials.js` приводит выбранные названия к точным Material ID перед поиском, поэтому скопированный откат использует те же материалы. Неизвестное или неоднозначное название не отправляется в поиск: нужно выбрать точный вариант из списка. Максимум — 8 материалов в каждом фильтре. Словарь `/api/materials` строится один раз из Material enum и существующего `RussianItems`/`ru_ru.json`, без обращений к БД или живым мирам; загружается при входе в панель.

После успешного поиска появляется команда `/co rollback` для ручного копирования. Она строится по проверенным backend фильтрам последнего поиска и охватывает все совпадения, включая другие страницы. Галочки/поля изменились — предложение скрывается до нового поиска. Команда никогда не отправляется серверу панелью; права CoreProtect при ручном запуске остаются обязательными.

Контракт сверён по [исходникам команд тега 24.1](https://github.com/PlayPro/CoreProtect/tree/v24.1/src/main/java/net/coreprotect/command): поддержаны `u:ник`, секундный диапазон `t:старшеs-моложеs`, `a:`, `i:`, `e:`, мир `r:#world`, координаты `c:x,y,z` и куб `r:RxRxR` (в том числе `0x0x0`). Повторный `r:` намеренный: WorldParser читает мир, LocationParser — числовую область. При отсутствии координат явно задаётся весь выбранный мир или `r:#global`, чтобы CoreProtect не применил радиус вокруг администратора по умолчанию. Время пересчитывается при копировании; вставлять команду нужно сразу, поскольку native-синтаксис использует относительный период. Для поиска с координатами команду запускают из того же мира: LocationParser 24.1 ограничивает Y текущим миром.

Генератор не подменяет UUID ником и не отбрасывает неподдерживаемые фильтры: native `u:` в 24.1 требует актуальный ник. Для списка всех категорий, чата, команд, табличек, сессий, отдельных item-транзакций и взаимодействий вместо команды показана причина. В категории блоков нужно выбрать поломку или установку. Контейнеры и inventory поддерживаются; inventory требует игрока онлайн. Для блоков и убийств дополнительно копируется `#preview`; для контейнеров/inventory предпросмотр в 24.1 не поддержан. Настройки и правила самого CoreProtect могут накладывать дополнительные ограничения на ручной откат.

## Физический read-only и нагрузка

Адаптер открывает отдельное JDBC-соединение с отдельным **SELECT-only пользователем**. При каждом соединении читает `SHOW GRANTS FOR CURRENT_USER` и отклоняет лишние привилегии, роли, GRANT OPTION, global SELECT; принимаются только USAGE и SELECT на указанную базу. `SHOW GRANTS` — чтение метаданных прав. Все запросы истории/схемы — фиксированные SELECT; arbitrary SQL не существует, multi-queries/local infile отключены. Дополнительно ставится JDBC readOnly. Основная защита от записи — права отдельной учётной записи, а не один флаг Java.

В интерфейсе источника и HTTP routes нет изменения данных или игровых команд. CoreProtect API используется только для проверки версии/isEnabled; rollback/restore/purge/log/write не вызываются. Не используется соединение основного CoreProtect. Миры и игроки Bukkit с HTTP-потоков не читаются.

Отдельный ограниченный executor: 1–4 поиска, по умолчанию 2, без очереди тяжёлых задач. Таймаут ответа/SQL 5 секунд, connectTimeout 2 секунды, socketTimeout ограничен. Если драйвер игнорирует interrupt, worker остаётся занят до окончания запроса — новый вместо него не создаётся. Результат и SQL LIMIT ограничены. Дополнительный небольшой bounded HTTP pool; rate limit на TG ID. Запрос без игрока и координат, чрезмерный период/радиус/размер страницы отклоняется backend. Производительность на реальной базе намеренно не проверялась; для первого включения начинайте с коротких периодов и concurrency 1.

## Что потребуется для включения позже

**Эти действия сейчас не выполнялись.**

1. Подготовить отдельную MariaDB-учётную запись, доступную только с машины сервера, с единственным SELECT на `coreprotect.*`. Не использовать root или учётную запись самого CoreProtect. Администратор БД может создать её отдельно; панель сама пользователей и grants не создаёт.
2. Настроить `coreprotectWeb` в `telegram.yml`: `enabled`, `accessChatId`, `publicUrl`, `bindHost`/`bindPort`, `database` и `limits`. Шаблон содержит комментарии. Пароль можно передать через `VAULT_COREPROTECT_VIEWER_PASSWORD`. Остальные существующие настройки не требуется менять.
3. Подготовить публичный HTTPS URL, например `https://admin.example.org/coreprotect/`, с доверенным сертификатом и reverse proxy к `http://127.0.0.1:8194/coreprotect/`. Сохранять путь и Authorization; HTTP доступ к локальному listener извне не открывать. Разрешить только GET, ограничить заголовки/частоту на proxy; не кэшировать ответы, не логировать Authorization. Если proxy на другой машине — нужен отдельно защищённый туннель, а не открытый listener.
4. Бот должен состоять в accessChatId и иметь возможность надёжно выполнять getChatMember для администраторов (боту нужны права администратора группы). Публичный URL указывается для того же бота, чей token использует VaultTracker.
5. Установить подготовленный JAR во время согласованного окна обслуживания. В этой задаче live JAR и конфиги не заменялись, restart/reload не выполнялся. Затем проверить вход с разрешённой учётной записью и отказ обычному игроку. До этого панель остаётся выключенной.
