## Названия топиков

Начиная с 0.17.75 фильтр, список и график показывают полученные из Telegram названия. Бот запоминает создание/переименование темы и узнаёт старую тему из ответа на её корневое сообщение. Название переживает перезапуск; старое имя из ответа не заменяет новое после переименования.

Если вместо имени остаётся ID, бот ещё не получил название. Отдельного метода чтения существующей темы по ID в Bot API нет. После установки нового JAR можно временно добавить символ к названию нужной темы в Telegram и вернуть прежнее название — бот получит событие и подпишет тему автоматически. Перезапускать Minecraft для изменения названия темы не нужно. Откройте приложение заново или подождите до 35 секунд для обновления списка; серверный cache — до 30 секунд. Старые сообщения при этом не добавляются в статистику.

## Где открыть

Кнопка **📊 Telegram-статистика** добавлена только в **🔐 Root → 📊 Аналитика**. Admin/SuperAdmin её не получают. Дополнительно Root должен быть administrator/creator группы `telegramAnalytics.accessChatId`. Обе проверки выполняются сервером, в том числе при чтении из cache. Отзыв Root действует сразу; проверка Telegram имеет прежний TTL 30 секунд.

Предлагаемый адрес — `https://flexity.fun/telegram-stats/`. Путь задаётся `publicUrl`, заканчивается `/`, отличается от CoreProtect. Это новый route на **том же localhost listener/порту**, по умолчанию 127.0.0.1:8194. CoreProtect продолжает работать по своему прежнему пути, с прежними настройками и правами. Analytics не зависит от доступности MariaDB/CoreProtect.

Общие: Telegram Mini App HMAC, возраст initData, проверка реального Telegram-admin, CSP, лимиты HTTP. У каждого приложения отдельный объект sessions и своя role policy: токен CoreProtect не открывает Analytics, и наоборот. Сессии короткие, bearer хранится только в памяти страницы; cookies/localStorage/URL для него не используются. Атрибуты HttpOnly/Secure/SameSite к отсутствующим cookies не применяются. Обычная ссылка показывает только приглашение открыть панель в боте. API только GET: `api/session`, `api/options`, `api/dashboard`. Ни удаления, ни backfill, ни произвольного SQL через web нет.

## Чаты и дата начала

С версии 0.17.76 успешные отправки VaultTracker и чат-моста Minecraft → Telegram включаются в число сообщений, активность тем, временные графики и контент. Оба подключённых бота учитываются и при разных токенах. Используется ответ `sendMessage`/`sendDocument` и других send/forward методов; Telegram не обязан возвращать собственную отправку в getUpdates. Multipart-документы и массивы сообщений тоже учитываются. Для `copyMessage` API возвращает только ID: сохраняется число публикаций с типом `other` и временем успешного ответа, без догадок о медиа/авторе и без изменения известного типа чата.

Боты не прибавляются к уникальным человеческим авторам, DAU/WAU/MAU или удержанию. Несколько игровых реплик, которые мост объединил редактированием одного Telegram-поста, считаются одним Telegram-сообщением. Повторы по chat/messageId не удваиваются. Неудачная отправка не считается опубликованным сообщением. Личные и невыбранные чаты исключены. Исторические исходящие сообщения до установки этой версии не восстанавливаются.

Сообщения посторонних ботов и других процессов нельзя обещать учесть полностью: [Telegram не передаёт ботам сообщения других ботов](https://core.telegram.org/bots/faq#why-doesn-39t-my-bot-see-messages-from-other-bots). Если соответствующий update всё же доступен (например, пост канала), он учитывается обычным способом. Получение/отправка сообщений игрокам из-за аналитики не запускается; дополнительных Telegram-запросов для учёта нет.

Сейчас **ни один чат не включён**: шаблон `enabled: false`, `trackedChats: []`. Группы/каналы не определяются автоматически по факту добавления бота. В существующих шаблонах есть общественная группа новостей и административная группа поддержки; их наличие само по себе не означает разрешение собирать рекламную аналитику. Поэтому нужно явно перечислить нужные chat IDs, до 100 в одном экземпляре (защитный предел, не hardcode двух сообществ).

Статистика начнёт накапливаться **после первого включения**, а не с даты разработки. У каждого чата сохраняются collectionStartedAt/earliestReliableAt, lastEventAt, heartbeat, известные интервалы пропусков, первая/последняя точка и число snapshots. UI показывает дату начала и неполные периоды. До наблюдений выводится «Нет данных», а не исторический ноль. Текущий незавершённый день также является неполным периодом.

Первоначальный backlog сообщений, созданных до collectionStartedAt данного чата, и edits таких сообщений не включаются в счётчики. Это сохраняет одну границу для messages/authors/heatmap и не превращает случайно доставленную старую правку в историческую статистику. После restart исходная граница остаётся прежней: новые сообщения, созданные во время последующих перерывов, могут прийти из обычной очереди Telegram.

Безопасный backfill не делался: существующие `GuardService.events`, `player_messages`, support и moderation repositories не содержат полного достоверного потока сообщений всех Telegram-чатов. Логи консоли, scraping и userbot не используются.

Telegram [хранит недоставленные updates не более 24 часов](https://core.telegram.org/bots/api#getting-updates), а getUpdates не является API произвольной истории. Privacy Mode, доступ бота, ошибки сети, работа другого poller и периоды выключения могут ограничивать фактически полученные события. Запись известного пропуска консервативна: после сбоя backlog может заполнить часть истории, но полнота не объявляется автоматически восстановленной. Удаления сообщений не отслеживаются; показатели отражают наблюдавшуюся публикацию, а не число сообщений, оставшихся в чате сегодня.

## Что сохраняется

Для сообщения: chatId, topicId, messageId, исходное время UTC, edit timestamp, стабильный HMAC-SHA256 ключ автора, тип сообщения, reply/forward/media flags, длина текста, признак служебного сообщения. Также названия/типы сообществ и наблюдавшиеся названия тем. Бот/анонимный sender_chat/пост канала без личного автора не создаёт фиктивного автора. Авторы считаются по наблюдаемым человеческим отправителям, а не по числу читателей.

HMAC secret создаётся один раз внутри этой H2-базы и переживает restart/reload. Он общий для tracked chats, поэтому один автор между чатами считается один раз. API не выдаёт ни hash, ни Telegram user ID. Пара chatId + messageId дедуплицирует сообщение; edit обновляет metadata и корректирует агрегаты транзакционно, не увеличивая число сообщений. Равные/старые повторы не удваивают активность. Reply на служебное сообщение создания forum-темы не выдаётся за пользовательский ответ.

**Не сохраняются:** текст/команды/подписи сообщений, private messages, содержимое медиа, usernames авторов, телефоны, фото профиля, IP-адреса, личная история в web. Raw JSON существует только во время получения: очередь содержит уже очищенные metadata. Analytics не пишет raw updates, user IDs, initData и session tokens в application logs. Названия чатов и тем выводятся как текст, не HTML.

## Хранилище и нагрузка

Отдельная **H2 `plugins/VaultTracker/telegram-analytics.mv.db`** использует уже подключённый JDBC-драйвер H2, без новой SQLite/native библиотеки и без соединения с guard-data/MariaDB. Версия схемы — 1; создание таблиц/индексов идемпотентно, более новая неизвестная версия отклоняется. Timezone сохраняется вместе со схемой: её изменение требует отдельной миграции/пересчёта, иначе запуск аналитики отклоняется вместо смешивания дней.

Основные таблицы:

| Таблицы | Назначение |
| --- | --- |
| ta_settings | Версия, timezone, постоянный HMAC key |
| ta_chats / ta_topics / ta_gaps | Покрытие, названия, известные пропуски |
| ta_messages | Минимальные metadata, identity chat+message |
| ta_daily / ta_hours / ta_heatmap | Типы, дневные/часовые счётчики, быстрая all-time heatmap |
| ta_user_days / ta_authors | Точные distinct authors, дневная активность, первое появление и дни активности |
| ta_snapshots | Замеры участников, idempotent по chat+interval bucket |
| ta_members / ta_member_days | Доставленные chat_member transitions и агрегаты входов/выходов |

**Retention = forever.** Автоматической очистки через 30/90/365 дней нет, кнопок purge/delete нет. Изменение allowlist прекращает новый сбор для исключённого чата, но не удаляет историю. Резервировать нужно всю H2-базу вместе с её secret; не подменять отдельные таблицы/ключ. Размер зависит от потока metadata и числа активных авторов/топиков, фиксированный размер на годы не обещается. Production-файл не создавался и его размер неизвестен. Root-раздел «Хранилище и покрытие» показывает фактические bytes, rows, earliest/latest timestamps и schema.

Сбор/SQL выполняются вне tick/region threads. Очередь 2048, один writer, batches до 100; нормальная остановка дожидается flush. Отдельный scheduler снимает участников; сообщения/рассылки при этом не отправляет. При переполнении/ошибке записи бот продолжает работать, а потеря помечается gap. При аварийном завершении между получением update и durable batch возможен пропуск; следующий запуск отмечает интервал. Утверждения «потерь никогда нет» нет.

Dashboard читает агрегаты, а не полный ta_messages. Точные distinct/cohorts читают компактные user activity tables; их стоимость всё же растёт с числом активных авторов/дней. Daily/hourly/user/member indexes ограничивают диапазоны. Диагностический COUNT и MIN/MAX metadata используют H2 direct lookup/index, проверено EXPLAIN. SQL timeout 5 с, один report worker без очереди тяжёлых запросов, HTTP timeout 8 с, cache 30 с/64 entries, rate 30/min. Cache key включает chat/topic/период/шаг/сортировку/timezone/metric. Даже при timeout не запускается неограниченное число дополнительных workers. Нагрузочных проверок на рабочей БД не было.

## Периоды, графики и определения

Сегодня, вчера, 7/30/90/180/365 дней, всё время и свои даты, в том числе несколько лет. Это календарные даты в настроенной timezone; timestamps в базе — UTC. Верхняя дата включительна. All-time означает всё наблюдавшееся время. Шаг: до 60 дней — дни, до года — недели, длиннее и all-time — месяцы; можно выбрать вручную. Для более 2000 дневных точек нужно выбрать недели/месяцы; сам период не обрезается.

Вкладки: **Обзор, Топики, Активность, Аудитория, Контент, Для рекламы**. Есть графики сообщений, уникальных авторов, аудитории, топиков, типов контента и heatmap Пн–Вс × 00–23. Обзор показывает сообщения, уникальных авторов, участников сейчас, изменение между snapshots, messages/day, messages/author и самый активный месяц. Графики не дорисовывают выдуманную старую историю.

Средние messages/day и active authors/day используют наблюдавшиеся календарные дни внутри выбора; старт до включения не создаёт искусственные нулевые годы в знаменателе. При разных датах начала/пропусках показывается ограничение покрытия. Активные авторы по неделям/месяцам — distinct за bucket, не сумма DAU. DAU/WAU/MAU привязаны к последнему дню выбранного периода и означают последние 1/7/30 календарных дней, даже если основной период короче.

Новый автор впервые наблюдался в выбранном чате; в «Все чаты» — впервые среди выбранных сообществ, с глобальным distinct. Переход в новый topic не делает автора новым в чате. Вернувшийся — был известен до начала выбранного периода и писал в нём. Отдельно считаются авторы, активные несколько разных дней. Retention: новые авторы → писали в следующие 7 календарных дней, начиная со следующего дня; в выбранной теме учитывается активность этой темы, старт автора берётся из чата. Cohorts без полного 7-дневного наблюдения или с известными пропусками не включаются в знаменатель, показываются отдельно. Это не дата вступления/регистрации Telegram.

Сравнение с предыдущим равным календарным диапазоном доступно только для двух завершённых покрытых периодов. При нулевом старом знаменателе процент отсутствует. В all-time и незавершённом текущем периоде сравнение не придумывается. Используется BigDecimal, не float для процентов/средних.

Топики сохраняют chat context: одинаковые topicId в разных чатах не объединяются. Таблица даёт messages, authors, share, messages/day, change; сортируется по активности/росту/падению/названию, по 50 строк, с переходом в тему. При наличии корректного сравнения видны и темы, которые замолчали в текущем периоде. Название берётся из увиденных forum_topic_created/edited; иначе «Тема #…». Списки/страницы имеют технические пределы, при очень большом числе тем нужно сузить чат. Рекламный топ тем всегда сортируется по активности, независимо от текущей сортировки Root-таблицы.

Типы контента определяются по реальным update fields; служебные события отдельно и исключены из messages/active authors/heatmap. Replies, forwards и media share — наблюдаемые доли. Reactions, просмотры, охват, демография и sentiment не заявляются и не подделываются.

## Аудитория: группа и канал

По умолчанию раз в 60 минут бот получает [getChatMemberCount](https://core.telegram.org/bots/api#getchatmembercount) и название/тип чата через getChat. Участников сейчас показываем только при достаточно свежем замере; отсутствие/устаревший snapshot — «Нет данных». График начинается с первой реальной точки, по timezone/шагу периода. Тема не имеет собственного member count.

Рост — разница первого и последнего реальных snapshot **в выбранном периоде**, процент — от первого; меньше двух точек означает «Нет данных». Это не точное число join/leave. Для групп отдельно показываются доставленные chat_member transitions; это точные наблюдённые переходы, но полнота доставки не гарантируется. Для каналов используются только snapshots, fictitious joins не вычисляются. Суммарное число участников нескольких чатов не устраняет пересечения людей; это явно написано в UI. Активные авторы между чатами дедуплицируются по HMAC независимо от суммы участников.

## Экран для рекламодателя

Закрытая Root-вкладка с агрегированной сводкой, выбранным периодом (включая 90/180/год/all/custom), динамикой, средними, пиковым временем, долей медиа, активными разделами и возвращениями/cohorts. Подходит для скриншота. Нет персональных IDs, usernames, индивидуальных историй, текста сообщений, токенов или технических полей хранилища. Название неидентифицированного чата/темы заменяется общим. Публичной ссылки без авторизации, advertiser login и автоматической отправки наружу нет. Активные авторы не называются охватом рекламы.

## Как включить позже, не меняя существующие ключи

1. Выбрать chat IDs нужных сообществ и группу для проверки Telegram-admin у Root. Не включать автоматически административную переписку в рекламную статистику.
2. Добавить **только** `telegramAnalytics` в существующий `telegram.yml`; не копировать поверх него весь шаблон из JAR. Сохранить текущие token, CoreProtect/MariaDB credentials и другие настройки. Пример значений (ID заменить своими):

```yaml
telegramAnalytics:
  enabled: true
  trackedChats: [-1000000000001, -1000000000002]
  timezone: "Asia/Novosibirsk"
  accessChatId: -1000000000001
  publicUrl: "https://flexity.fun/telegram-stats/"
  memberSnapshotMinutes: 60
```

Если `accessChatId` отсутствует, используется значение CoreProtect. Shared host/port берутся из `coreprotectWeb.bindHost/bindPort`, даже при выключенном CoreProtect; пароль MariaDB для Analytics не требуется.

3. Бот/настроенные боты должны получать события из перечисленных чатов/каналов. Для полного потока обычных групповых сообщений нужны права/Privacy Mode согласно настройкам Telegram; для chat_member бот должен быть администратором и явно запрашивать этот update type. Analytics запрашивает message edits/channel posts/chat_member только когда включена. Второй poller с тем же токеном не запускается: используется существующий polling; при отдельном токене чат-моста capture подключается и к нему. Реакции дополнительно не запрашиваются.
4. На существующем HTTPS proxy добавить отдельный handler `/telegram-stats/*` → `http://127.0.0.1:8194`, сохраняя путь/Authorization, только GET, без access-log query/headers и без cache. `/telegram-stats` перенаправить на `/telegram-stats/`. Существующий `/coreprotect/*` не изменять. **Новый публичный порт/DNS/сертификат для этого не требуется.** Пример Caddy-фрагмента для дальнейшего review, сейчас не применялся:

```caddyfile
handle /telegram-stats/* {
    log_skip
    @analyticsWrite not method GET
    respond @analyticsWrite 405
    reverse_proxy 127.0.0.1:8194 {
        transport http {
            dial_timeout 2s
            response_header_timeout 12s
        }
    }
}
handle /telegram-stats {
    redir * /telegram-stats/ 308
}
```

5. Пользователь устанавливает новый JAR в плановое окно перезапуска. Общую `/reload` не использовать. Затем проверить вход Root, отказ Admin/обычному пользователю и первый snapshot. Перед первым полученным событием и накоплением минимум двух точек аудитории часть карточек закономерно пустая. Production-действия из этого списка в задаче не выполнялись.
