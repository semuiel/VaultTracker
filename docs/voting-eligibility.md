# Голосования: право на награду и ТОП-3

## Единственный источник начислений

VotifierPlus → прежняя H2 outbox VaultTracker → API Python → `VoteRepository.accept/resolve` → существующий `Ledger` и общий кошелёк. Webhook и reconcile используют тот же repository. Java не начисляет вторую независимую награду.

До исправления `vote_interval_minutes` влиял только на текст Telegram. `resolve` проверял id события, но не право UUID на новую награду. События с другими timestamp/replay keys оплачивались повторно.

Теперь период скользящий: от фактического предыдущего начисления. Минимум 1440 минут. Старые 0 и значения меньше 1440 не выключают ограничение. Более длинный настроенный интервал сохраняется. Полночь и смена timezone не обнуляют таймер. Новый интервал записывается для следующего начисления; уже сохранённый nextEligibleAt остаётся источником решения и отображения.

В `vote_eligibility` PRIMARY KEY(owner,provider) хранятся last_credited, next_eligible и event_id. Canonical provider: minecraft_rating / top_minecrafter / hotmc. Ник сопоставляется Java с UUID; смена ника не даёт новую награду.

В одной SQLite `BEGIN IMMEDIATE` транзакции проверяются eligibility и ledger key `vote:<event-id>`, меняются кошелёк/credited, сохраняются новый cooldown и уведомление. Конкурирующие процессы сериализуются SQLite. Потеря HTTP-ответа не меняет уже сохранённый результат. Ошибка до commit откатывает все части; retry может выдать положенную первую награду.

Событие внутри cooldown получает технический статус `cooldown`. Оно не меняет баланс, последний credited, следующий срок, уведомления и месячный рейтинг. Если накопилось несколько pending одного provider, за один момент resolve оплачивается максимум один. История timestamp не используется для пакетной выплаты нескольких прошлых дней в обход текущего ограничения.

При первом обращении после обновления cooldown восстанавливается из последнего прежнего credited. Если голос был до обновления менее 24 часов назад, повторное начисление тоже блокируется. Старые балансы, записи и уже отправленные уведомления не удаляются.

При награде 200 minor единиц три допустимых голоса дают максимум 600 = 6.00 монет. Настраиваемые награды продолжают работать; 6.00 не hardcode.

## Таймер

`/voting-providers` с owner возвращает eligibilityKnown, nextEligibleAt и remainingSeconds из того же сохранённого состояния, которое проверяет resolve. При отсутствии достоверного поля Java пишет «Статус награды пока недоступен», а не «Доступно». При ошибке API меню сообщает недоступность. Кнопка «Обновить» заново читает сервис; фонового ежесекундного редактирования нет.

Если в существующем telegram-menu.yml переопределён старый `texts.voting.user`, при плановом обновлении замените только заголовок на «🗳 Голосования», сохранив `{providers}`. Встроенный шаблон уже обновлён. Не заменяйте весь конфиг своими значениями из примера.

## Месячные призы

Root → Экономика → Голосования и награды → Призы ТОП-3. Три независимые суммы с подтверждением, по умолчанию 300/200/100 для новой установки. Существующий приз первого места сохраняется, включая ранее установленный 0; второй и третий добавляются с 200/100. Настройки переживают рестарт. Отрицательные суммы и более двух десятичных знаков UI отвергает.

Рейтинг суммирует только `status='credited'`, по времени начисления, для календарного месяца с прежним offset (по умолчанию UTC+7). При равенстве используются competition ranks: 1,1,3 и 1,2,2. При четырёх равных вторых местах призёров может быть больше трёх. У одного UUID один ранг.

`full` даёт каждому приз его ранга. `split` делит сумму этого ранга между всеми на нём; остаток minor единиц распределяется по UUID по возрастанию. Пропущенный ранг никому не оплачивается. Нулевые голоса не награждаются.

Существующий scheduler закрывает месяц одной транзакцией: immutable result/settings snapshot, ranks, prizes и кошелёк. Ключ первого места остаётся `vote-month:<month>:leader:<UUID>`, далее `place2`/`place3`. Повторный settlement ничего не доплачивает. Миграция monthly_top_three/1 помечает исторические суммы 2/3 нулевыми; прежние закрытые месяцы не пересчитываются. Eligibility migration — отдельная eligibility/1 в vote_schema_migrations.

## Безопасная сверка прежней истории

Автоматического исправления старых переплат нет. Новое ограничение не доказывает, какие старые события были ошибочными. Для будущей проверки сначала сделайте согласованную резервную копию после остановки только платёжного сервиса и исследуйте копию:

```sql
WITH paid AS (
  SELECT owner,provider,id,credited,actual_reward,
    LAG(credited) OVER(PARTITION BY owner,provider ORDER BY credited,id) AS previous
  FROM vote_events WHERE status='credited'
)
SELECT * FROM paid WHERE previous IS NOT NULL AND credited-previous<86400
ORDER BY owner,provider,credited;
```

Это список кандидатов на сверку, не команда возврата и не доказательство злоупотребления. Сопоставьте события/ledger, правила площадки и прежние настройки. Не удаляйте credited/ranks/entries и не запускайте повторное закрытие исторических месяцев. Если понадобится корректировка, оформляйте отдельную согласованную операцию с аудитом.
