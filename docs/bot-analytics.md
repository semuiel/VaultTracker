# Аналитика использования бота

Отдельная Root Mini App. Статистика сообщений общих и административных чатов остаётся в прежней Telegram-статистике. Исходящие сообщения бота и Minecraft bridge не становятся действиями пользователей.

## Сбор и каталог

`BotAnalytics.begin` создаёт контекст update ID и снимок существующей роли GuardService. `TelegramActionRegistry` регистрирует все свои маршруты (в том числе direct и prefix), их владельца, правила аргументов и требуемую роль. Для административных confirm/do учитывается только фиксированный вид операции, без цели и текста. `/api/options` возвращает актуальный каталог, включая появившиеся явные business hooks. Локальная инвентаризация исходников — `bot-analytics-catalog.md`.

Типы событий: screen_view, button_click, flow_start, form_submit, operation_success, operation_failure, operation_denied, flow_complete. Открытие формы не является её успешным завершением. Открытия здесь означают построенный обработчиком экран, а не подтверждение прочтения Telegram-пользователем.

Нажатия/экраны покрывают кабинет, ресурсы/историю, друзей/доступ, сообщения, настройки, личную статистику, поддержку, пожертвования/премиум, Free-монеты/голосования, административные и Root-разделы. Обычные поля форм дают только имя вида ввода до `:`, без содержимого. CoreProtect Mini App помечается отдельной функцией и не смешивается с торговым поиском.

Явные успешные результаты подключены после подтверждённого ответа backend для покупки премиума, redeem платежа, награды за привязку, сохранённого обращения, привязки в GuardService, настроек уведомлений/сортировки/тега, друзей/доступа и сохранения личного сообщения. Изменения статусов обращений учитываются после успешного сохранения. Остальные административные экраны и команды имеют нажатия/отказы, но не выдуманный business success по тексту ответа игры. Их полный исход не гарантируется, если существующий API возвращает только строку; количество нажатий не является количеством наказаний или успешных команд.

Привязка завершается асинхронно на worker GuardService после записи аккаунта. Покупки и обращения используют стабильный ключ результата, поэтому новый update с повторным подтверждением той же операции не создаёт ещё одну покупку/завершение. Воронки хранят начало, отправку и завершение по псевдопользователю/функции; завершение связывается с последним незавершённым сценарием. Успех без наблюдавшегося начала не создаёт выдуманный старт. Это аналитика сценариев, а не замена финансовому аудиту.

## Поиск

TelegramPrivateMenu считает открытие поиска, выбор player/item, фильтрацию списка и пагинацию. TelegramCommands регистрирует фактически выполненный поиск: canonical Material/AR/IR либо найденный публичный ник, число результатов, способ ввода, язык ru/en/unknown и время обработки до события результата. Это время обработки запроса, включая маршрутизацию, а не отдельный SQL benchmark.

`search.filter` и `search.result` показаны раздельно. Пагинация не становится новым поисковым запросом. Пустой/неразобранный ввод не хранится. Повторы считаются по одному псевдопользователю и распознанному предмету/найденному публичному нику, без раскрытия индивидуальной истории. Групповые команды поиска могут учитываться, если прошли существующие правила чата; сообщения группы сами по себе не учитываются.

## Хранение и точность

Отдельный `bot-analytics.mv.db` в каталоге плагина: schema version 1, стабильный HMAC key, минимальные events, hourly/daily user aggregates, sessions и flows. Автоматического удаления/TTL истории нет. Сохраняйте файл и резервные копии; бессрочное хранение не заменяет backup. Не копируйте активную H2 отдельно от согласованного backup.

Event ID — HMAC стабильного update/operation key и вида события. Retry одного update не дублируется; новое настоящее действие имеет новый update ID. Очередь ограничена 4096 событиями, один worker пишет до 100 за транзакцию. Основная логика не ждёт JDBC. Штатное закрытие дожидается очереди; аварийное завершение процесса может потерять ещё не записанный хвост. Потери очереди/ошибки записи и перерывы после heartbeat выводятся как неполное покрытие. Сбор не восстанавливает произвольную историю Telegram Bot API и не делает backfill из консоли.

Сессия — действия пользователя с паузами менее 30 минут; ровно 30 минут начинает новую. DAU/WAU/MAU относятся к последнему дню выбранного периода и окнам 1/7/30 дней перед ним. Новые — впервые наблюдавшиеся после включения, не обязательно впервые использовавшие бота за всю его жизнь. «Одна сессия» относится к выбранному периоду. D1/D7/D30 — точный календарный день возврата; ещё не закончившийся день исключён. При пропусках сбора retention может быть занижен: смотрите покрытие. Роли фиксируются на момент события; один человек с разными ролями может входить в несколько строк разбивки.

Все вкладки применяют период, роль и функцию. Timezone берётся из botAnalytics.timezone и фиксируется вместе с агрегатами; смена после начала отклоняется, чтобы не испортить существующие дни. Поддержаны сегодня/вчера/7/30/90/180/365 дней, all-time и диапазоны от 2000 года, включая несколько лет. Есть сравнение равного предыдущего периода, без ложного нуля при отсутствии покрытия. Запросы читают агрегаты с индексами, timeout и ограниченным executor/cache; event journal не сканируется каждой карточкой.

## Приватность и API

Не сохраняются тексты переписки/заявок, произвольный ввод, платёжные или link codes, initData, session tokens, API keys и содержание Root console. Telegram ID заменяется стабильным HMAC. Dashboard не отдаёт псевдо-ID, индивидуальные запросы и связи «кто что искал»; популярные публичные ники и Material IDs выводятся только агрегированно.

GET `/bot-analytics/api/session` проверяет Telegram initData, затем одновременно Root и Telegram administrator/creator административного чата. GET options/dashboard требуют отдельный короткий Bearer session. Повторная проверка роли и Telegram ACL с прежним TTL, Origin/CSP/no-store/rate limits, никакого доверия user= в URL. Admin и SuperAdmin доступа не получают. HTTP mutation/console/SQL endpoints отсутствуют. Сессии CoreProtect и статистики чатов не переиспользуются.

Вкладки: обзор, поиск, функции, пользователи, воронки, ошибки, администрирование. Графики: активность, новые/вернувшиеся, запросы player/item, heatmap, этапы воронок, ошибки, retention, месяцы и динамика популярных функций. Малоиспользуемые функции не включают технические Root-разделы в сравнение с игроками. Если событий ещё нет, низкую конверсию не следует интерпретировать как проблему продукта.
