# Работа с архитектурой VaultTracker

- Перед любой задачей сначала прочитай `docs/architecture.md` и используй её как карту проекта.
- Не изучай весь проект заново, если карта уже указывает нужные файлы и слои.
- Если задача изменила архитектуру, маршруты, расположение логики, добавила экран, handler, service или точку входа, обнови только соответствующий раздел `docs/architecture.md`.
- Если архитектура не изменилась, не трогай `docs/architecture.md`.
- Держи карту компактной: только актуальные пути и связи, без истории изменений и длинных описаний.

## Передача и объединение с FLEXITY

- Текущий исходный проект — корень этого репозитория: `src/`, `donations/`, `docs/`, Gradle Wrapper. Старая вложенная `VaultTracker/`, `work/`, `outputs/` не являются актуальными исходниками.
- Для знакомства следующего разработчика читать `docs/handoff.md`, для объединения — `docs/flexity-integration.md`. Указатель всех source/test-файлов — `docs/code-index.md`.
- Исходники самого FLEXITY находятся отдельно. Не придумывать его API по названию: сверять адаптер и конкретную передаваемую версию FLEXITY.
- Рабочий Minecraft с игроками не останавливать, не перезагружать и не выполнять команды/пересканы ради разработки. Production только read-only, пока владелец явно не поручил конкретное применение. Не использовать PlugMan/hot reload как процедуру установки.
- Сохранять серверную проверку Admin/Super/Root/capability и Telegram-admin ACL. OP и Root не равны; скрытая кнопка не является авторизацией.
- Не запускать второй poller с тем же live Telegram-токеном или второй платёжный процесс с live SQLite/FunPay. Проверки — временные базы, fixtures и отдельный стенд.
- UUID, server-id, финансовая idempotency, durable outbox, update offsets и HMAC keys не менять при переносе без отдельной миграции.
- Секреты, базы, runtime, backups и данные игроков в публичный Git не добавлять. Изменения исходников проверять командами из README; не объявлять тесты выполненными по старому отчёту.
