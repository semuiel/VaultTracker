# Пожертвования, премиум и голосования

Версия исходников в этом репозитории — 0.17.77. Для нового администратора: [передача и сборка](../docs/handoff.md), [карта модулей](../docs/architecture.md), [cooldown и ТОП-3](../docs/voting-eligibility.md). Рабочие config.local.json, donations.sqlite, runtime/lib и ключи не входят в Git. Архив исходников собирается из корня командой `python tools/package-payment.py`.

Проверка оплаченного заказа FunPay и доставка кода проверены на тестовом подключении. Новые покупки премиума и админские операции проверены автоматическими тестами; проверка выдачи на живом сервере LuckPerms остаётся отдельным этапом. Основной сервер с игроками не перезапускать ради настройки.

## Схема

Один лот: 1 шт. = 1 монета, базовая цена 1 ₽. Комиссии FunPay/платёжного метода оплачиваются сверх базовой стоимости и не превращаются в монеты. Количество берётся из карточки проверенного заказа, не из сообщения покупателя.

После оплаченного заказа сервис отправляет покупателю 128-битный случайный код. Ввод кода в связанном Telegram-кабинете вызывает повторную проверку заказа на FunPay и атомарное зачисление по UUID персонажа. Root-пользователи получают отдельные уведомления о зачислении, подтверждении заказа, бонусе за отзыв и возврате. До подтверждения заказа зачисление видно в балансе, но недоступно для покупки премиума и списания через сайт; после закрытия заказа оно становится доступным. После фактической оценки закрытого заказа начисляется однократный бонус: 1–5 звёзд дают соответственно 1–5%, с округлением вниз до сотой монеты. Отсутствующая или некорректная оценка бонуса не даёт. Учитывается также оценка без текста по блоку отзыва заказа; актуальную разметку необходимо проверить на контрольном заказе.

Возврат отменяет пополнение и бонус один раз. Сервис проверяет точный заказ в списке возвратов продавца, если метка на странице заказа отсутствует; для уже учтённого заказа он может взять сумму из своей записи, когда FunPay больше не показывает количество. Если монеты уже потрачены, баланс может стать отрицательным, выставляется флаг blocked и создаётся уведомление Root-пользователям. Покупки премиума и списания сайта проверяют blocked и доступный баланс в одной транзакции. Возврат не снимает уже выданные услуги автоматически; Root-пользователь видит уведомление и может снять премиум в меню.

## Премиум и управление балансом

Код пополнения можно отправить в личный чат бота без открытия меню и без срока ожидания ввода. В разделе «Премиум» сначала выбирается тариф, затем срок. 1 месяц сохраняет прежнюю семантику 30 дней: 1/2/6/12 месяцев = 30/60/180/360 дней.

| Тариф / группа LuckPerms | 1 месяц | 2 месяца | 6 месяцев | 12 месяцев |
| --- | ---: | ---: | ---: | ---: |
| Premium Lite / `premiumlite` | 319 | 549 | 1490 | 2690 |
| Premium / `premium` | 600 | 1000 | 2700 | 4800 |

Цены в монетах. Группы должны существовать в LuckPerms; при отсутствующей группе деньги не списываются. Выдача идёт через API с абсолютной датой окончания, включая офлайн-игроков. Каждый тариф продлевает собственный оставшийся срок, автоматического обмена дней между тарифами нет. Бессрочный тариф не заменяется платным временным. Верхняя карточка показывает каждый активный тариф и его срок. [Описание возможностей для игроков](../docs/premium-free-coins.md).

Баланс и новая дата тарифа сохраняются атомарно. Очередь применения переживает перезапуск; подтверждение выдачи записывается только после успешного сохранения LuckPerms. При сбое после оплаты повторное применение не списывает деньги повторно. В меню показывается ожидание применения. Синхронизация меняет только выбранную группу. Старые покупки и административные выдачи по умолчанию относятся к `premium`. Таблица `premium` сохраняется; `premium_lite` имеет ту же схему с независимыми сроками и версиями. `/premium-tasks` отдаёт Lite только клиенту с `includeLite: true`; старый клиент не сможет применить Lite как Premium. `/premium-ack` и `/donation-change` принимают `product` (`premium` по умолчанию).

## Free-монеты и награда за привязку

Меню пожертвований: «Пополнить», «Премиум», «Free-монеты», «Меню». В «Free-монеты» находятся прежнее голосование и разовая награда за связь Minecraft ↔ Telegram. Несвязанный пользователь получает существующую команду привязки, деньги до неё не начисляются. Все старые привязки также имеют право получить награду.

По умолчанию награда 150 монет. Root меняет её в «Управление пожертвованиями → Награда за привязку» через числовой ввод и подтверждение. Новая сумма действует только на будущие получения; ноль допускается, но получение даже нулевой награды остаётся одноразовым. Проверка роли выполняется при вводе и подтверждении. Website API key к наградам и настройкам доступа не имеет.

`LinkRewards` хранит `link_reward_claims` с PRIMARY KEY по каноническому Minecraft UUID. В одной транзакции сохраняются факт получения, фактическая сумма, строка `entries` с ключом `link-reward:UUID` и source `LINK_REWARD`, изменение общего кошелька и аудит. Telegram ID — только исполнитель в аудите, он не определяет право на награду. Повторный callback, смена Telegram, unlink/relink и перезапуск не дают вторую выплату. Java перед каждым claim проверяет текущую привязку через GuardService. После получения кнопка скрыта. Награда не снимает блокировку долга после возврата.

Миграция добавляет колонку `entries.source`, таблицы `link_reward_settings`, `link_reward_claims` и `premium_lite`, не помечая старые привязки полученными. Локальные API: `/link-reward-settings`, `/link-reward-update` и `/link-reward-claim`, доступны только основному ключу сервиса. SQL не находится в Telegram-меню.

Для возможностей тарифов используются существующие LP-группы; VaultTracker не создаёт и не переписывает их permissions. Запись кастомных пластинок описана как возможность Premium по требованиям сервера. Проверенного контракта permission для неё в доступном VaultTracker/API нет, поэтому выдуманные nodes не добавлены.

Minecraft-команда `/unlink` теперь требует именно `player.isOp()`. Обычные permissions не обходят эту проверку; `/vtrack link` не ограничен дополнительно. Консольная отвязка по-прежнему не поддерживается. Нового `/vtrack unlink` нет.

Суперадминистратору доступны выдача на 30/60 дней, собственный срок от 1 до 36 500 дней, бессрочный премиум, снятие, начисление/списание баланса и журнал с Telegram ID исполнителя, игроком, действием, суммой/сроком и датой. Списать больше баланса нельзя. Все списки игроков имеют страницы по 20 строк, поиск, онлайн/офлайн. Журнал — 20 записей на страницу.

Интеграция второго плагина сайта описана в [BALANCE-API.md](BALANCE-API.md): общий баланс, отдельный ограниченный ключ и идемпотентные операции.

## Обновление сервиса

При запланированном обновлении остановите только сервис, сохраните резервную копию его папки и установите весь комплект Python-файлов соответствующего релиза, включая новые `premium_products.py` и `link_rewards.py`, а также существующие модули `vote_monthly.py`/`vote_reconcile.py`. Запустите прежний `START.cmd`. Не заменяйте `config.local.json` и не удаляйте `donations.sqlite`, WAL/SHM. Это по-прежнему один процесс и одно окно. Новые таблицы добавятся автоматически, существующие балансы сохранятся. Для новой версии Java-плагина требуется штатный перезапуск выбранного Minecraft-сервера. Для отката старого сервиса используйте согласованный комплект старого кода и резервной базы: старая запись `entries` не знает новой колонки `source`. В рамках разработки никаких обновлений production не выполнялось.

## MinecraftRating

Для награды за голос конкретного сервера MinecraftRating отправляет голос в VotifierPlus. На странице сервера укажите публичный адрес и внешний TCP-порт, публичный ключ возьмите из `plugins/VotifierPlus/rsa/public.key`. В роутере внешний порт направляется на внутренний порт из `plugins/VotifierPlus/config.yml`.

Добавьте в закрытый `config.local.json` секцию `voting` по образцу `config.example.json`. `reward_minor: 500` означает 5.00 монет, а `vote_url` ведёт на страницу конкретного сервера. Для Votifier-варианта `callback_enabled` и `reconcile_enabled` оставьте выключенными. Root меняет enabled и reward; изменения сохраняются в SQLite и действуют на будущие голоса.

VaultTracker сохраняет событие VotifierPlus в локальной H2-очереди до ответа платёжного сервиса. Временная остановка Python-процесса поэтому не теряет голос. После начисления Python-сервис хранит отдельное уведомление до успешной отправки связанному Telegram-пользователю.

Валидный голос сохраняется как pending, пока Java не сопоставит ник с единственным известным серверу UUID. Затем `vote:<internal-id>` атомарно зачисляет reward в общий donation wallet, а событие получает UUID, отображаемый ник, provider, source/received/credited timestamps и фактическую сумму. Повтор одного события не начисляет награду второй раз.

Для нового сайта добавьте подкласс `VoteProvider` в `vote_providers.py`, его config и регистрацию в `configured_providers`. Общие таблицы, начисление, статистика и Java UI менять не требуется.

Root-аналитика разделена на экраны: количество голосов по периодам, уникальные игроки и топ голосующих,
начисления и средняя награда, а также разбивка за последние семь дней. Те же разделы доступны отдельно
для каждого ресурса. Расчёты выполняются по сохранённым событиям голосования; сырые события не удаляются.
Локальный `/player-summary` возвращает кошелёк, статус премиума и число зачисленных голосов игрока по каждому ресурсу для административной карточки.

### Top-Minecrafter

Источник `top_minecrafter` добавлен отдельно: ссылка
`https://top-minecrafter.com/server/flexity/`, своя награда и статистика в Root.
Секция конфигурации есть в `config.example.json`. По умолчанию источник выключен.
По [официальной инструкции](https://top-minecrafter.com/help/votifier/) сайт использует Votifier v1
с serviceName `top-minecrafter.com`; это имя настроено по умолчанию.
Оба сайта используют один VotifierPlus, публичный ключ и открытый TCP-порт.
Неизвестный или неоднозначный serviceName не начисляет монеты; событие сохраняется
в локальной очереди. После исправления настройки и перезапуска платёжного сервиса оно будет обработано повторно.
Не следует включать источник для игроков до проверки настоящим голосом.

### HotMC

Источник `hotmc` использует страницу голосования
`https://hotmc.ru/vote-281777`, отдельную награду и отдельную статистику в Root.
HotMC подключается к тому же VotifierPlus, публичному ключу и TCP-порту 8192;
открывать ещё один порт не требуется. В настройках HotMC используются адрес сервера,

«Классический Votifier», а подтверждённый настоящим голосом serviceName — `HotMC.RU`.

## Отдельный процесс

### Готовая переносимая сборка Windows

В ранее подготовленной переносимой Windows-папке есть собственный Python в runtime: системный Python и Java не меняются. Сам runtime не входит в этот Git и исходный ZIP. Для чистого клона используйте venv по инструкции ниже. `SETUP.cmd` принимает golden_key скрытым вводом и определяет ID продавца. `CHECK.cmd` только проверяет авторизацию и доступ к продажам, ничего не отправляет и не начисляет. `START.cmd` запускает обработку; окно нужно оставить открытым. Эти CMD-скрипты рассчитаны на runtime/python.exe. Запускать сервис на самом компьютере Minecraft, не на клиентском ПК через сетевой диск. Вариант конфигурации `seller_id: 0` определяет продавца по авторизованному аккаунту; чужие заказы всё равно отвергаются. Ненулевой ID дополнительно фиксирует ожидаемый аккаунт.

Можно также заполнить только поле `golden_key` в уже подготовленном закрытом `config.local.json`. Остальные значения не менять. Проверка отдельного заказа без отправки сообщений и начислений: `runtime\python.exe service.py --config config.local.json --check-order ORDER_ID`.

Переносимый Python 3.13.15 получен с https://www.python.org/downloads/release/python-31315/ и проверен по опубликованной SHA-256. Зависимости установлены из PyPI; сведения о лицензиях находятся в `runtime/LICENSE.txt` и каталогах `lib/*.dist-info`. Исходники FunPayAPI 1.1.0 доступны на https://pypi.org/project/FunPayAPI/1.1.0/#files .

Сервис запускается на том же компьютере, где работает Minecraft, в отдельной папке вне каталогов миров и других плагинов. Он не обращается к Crafty, RCON, игровым файлам или консоли. По умолчанию HTTP слушает только 127.0.0.1:18763; внешний bind нужен лишь для прямого callback MinecraftRating. Финансовый API требует отдельный случайный ключ и при любом bind принимает запросы только с localhost. Клиент плагина обращается к нему только из Telegram-потоков, с ограниченным временем ожидания.

Зависимость FunPayAPI 1.1.0 — неофициальная библиотека из PyPI. Разметка сайта меняется: неизвестные статусы, количество и чужие заказы отвергаются, деньги по догадке не начисляются. Перед эксплуатацией нужно проверить адаптер на реальной карточке именно вашего заказа. Не передавайте golden_key посторонним: он даёт доступ к аккаунту продавца. Открытый в браузере аккаунт сам по себе не авторизует отдельный процесс.

1. В отдельной папке создать Python 3.11+ venv: `python -m venv .venv`.
2. Установить зависимости в venv: `.venv\Scripts\python -m pip install -r requirements.txt`.
3. Скопировать config.example.json в config.local.json. Файл доступен только владельцу сервиса.
4. Локально заполнить golden_key своего аккаунта; не отправлять его в чат и GitHub. seller_id=0 автоматически определяет продавца, либо задайте его ID явно. Сгенерировать api_key: `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Использовать один и тот же ключ в конфиге сервиса и VaultTracker/donations.yml.
5. Указать точное уникальное название лота в order_marker, category_id=1753 для «Донат Minecraft». Не менять название уже проданного лота в конфиге: старые заказы должны продолжать проверяться. Сначала закончить контрольный заказ; при изменении разметки обновить адаптер.
6. Запуск: `.venv\Scripts\python service.py --config config.local.json`. Запускать на сервере, а не с клиентского ПК через сетевой диск. Настройку автозапуска сделать отдельной задачей без перезапуска основного сервера.
7. В donations.yml плагина указать URL своего лота, api-key и enabled: true. Чтение этого файла выполняется при обращении к меню. Новый JAR устанавливается при согласованной остановке сервера.
8. В меню супер администратора включить кнопку пожертвований. По умолчанию она скрыта.

SQLite хранится рядом с конфигом, файл donations.sqlite; нельзя удалять его, иначе будет потерян журнал защиты от повторной выдачи. Для резервной копии использовать SQLite backup API или остановить только платёжный сервис и скопировать его БД вместе с WAL/SHM. Не копировать конфиги с секретами в публичные архивы. При сбое ответа после зачисления игрок вводит тот же код: повторного зачисления не будет.

Проверки запускаются `python -m unittest discover -s donations -v` из корня проекта. Плагин для Folia 26: `gradlew test shadowJar`; вариант 1.21.11: `gradlew -Plegacy=true test shadowJar` (JDK 21). Файлы разных вариантов нельзя одновременно помещать в plugins.

Персональный таймер каждого сайта задаётся в `voting.providers.<provider>.vote_interval_minutes` (целые минуты). По умолчанию 0: интервал не задан, таймер не показывается; это не проверка допустимости голоса на сайте. Задайте фактический интервал отдельно для каждого ресурса. Таймер рассчитывается из последнего `credited` события для UUID, не из нажатия ссылки; URL остаётся доступным.

Месячный «Топ голосов» суммирует `credited` события всех сайтов по UUID и времени начисления. Календарная зона задаётся `voting.calendar_utc_offset_minutes`, по умолчанию 420 (UTC+7). Pending-голос попадает в месяц, когда найден UUID и выполнено начисление. SQL выдаёт страницы по 10 игроков; смена ника не разделяет UUID. Root задаёт месячный приз и режим ничьей через подтверждение: `full` — каждому лидеру вся сумма, `split` — разделить фонд с детерминированным остатком копеек по UUID. Начальные значения: `monthly_reward_minor: 0`, `monthly_tie_policy: full`; после первой настройки актуальное значение хранится в БД, config — только начальное значение.

`vote_monthly.py` проверяет завершённые месяцы при запуске и раз в минуту. `vote_month_results` фиксирует сумму и режим; `vote_month_ranks` — итоговый рейтинг; `vote_month_prizes` — тип `leader`, место и выплату. В одной транзакции сохраняются результат и записи кошелька `vote-month:<YYYY-MM>:leader:<UUID>`. Сбой откатывает всё, повтор не начисляет заново. История не удаляется; локальный авторизованный API `/voting-top` принимает `month: YYYY-MM`, `page: 0` для просмотра закрытого результата. Месяц без голосов не даёт выплату.

Root → «Управление пожертвованиями» → «Статистика» показывает сегодня (полночь в зоне компьютера сервиса), последние 7/30 суток и всё время. SQL считает реальные пополнения и уникальные UUID донатеров, возвраты, бонусы отзывов, покупки и ручные активации премиума. Ручные add/subtract Root выводятся отдельно с итоговой знаковой суммой. «Подтверждено» — сумма пополнений выбранного периода, чьи заказы сейчас CLOSED; это не сумма событий подтверждения за этот период. Возвраты включают возвращённый бонус, а бонусы — исторически выданные суммы, поэтому эти строки не следует складывать как чистую выручку. Голоса и месячные призы не считаются платежами. Финансовая семантика операций остаётся прежней.

При обновлении сервиса нужен новый `vote_monthly.py` вместе с `voting.py`, `ledger.py` и `service.py`. Сохраните существующие `config.local.json` и `donations.sqlite`; новые настройки добавляются вручную, пример не заменяет рабочий конфиг.

### Суточная защита и месячные призы (0.17.77)

Начисление теперь проверяет persisted UUID/provider eligibility в одной транзакции с кошельком. Интервал — минимум 24 часа от начисления; старый 0 больше не выключает защиту. Технические повторы не меняют таймер, рейтинг и уведомления. ТОП-3 использует три суммы и прежние full/split, закрытые месяцы не доплачиваются. Обязателен весь комплект модулей, включая новый vote_schema.py. Подробности, историческая сверка и будущая установка: docs/voting-eligibility.md и docs/release-0.17.77.md в исходном проекте.
